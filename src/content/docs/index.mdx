## The gap between a demo and a deployment is operational.

Getting an agent to work is a weekend. Getting it into production is the actual job: which model,
at what cost ceiling; what the agent may say and do; who signs off before it touches a payment API;
how a new prompt is proven before it serves real traffic; and what exactly happened at 2&nbsp;a.m.
when a run went sideways.

Today every team answers those with bespoke glue — a proxy here, a script there, a spreadsheet of
prompts. **ctxmesh makes each answer a Kubernetes resource:** versioned, code-reviewed, reconciled
by an operator, and fail-closed when something's missing.

<div class="mapping not-content">
  <div><span>Which model, with what fallback and budget?</span><code>ModelRoute</code></div>
  <div><span>What may it say? What must it never leak?</span><code>GuardrailPolicy</code></div>
  <div><span>Who approves the dangerous tool call?</span><code>ApprovalPolicy</code></div>
  <div><span>Is the new version actually better?</span><code>EvalSuite</code></div>
  <div><span>How does it reach 100% of traffic?</span><code>spec.rollout — canary + auto-rollback</code></div>
  <div><span>What happened, step by step, and what did it cost?</span><code>the trace — no instrumentation</code></div>

<section class="band feature-row">
<div class="feature-copy">

<p class="eyebrow">Governance</p>

### Fail-closed, enforced in the pod — not middleware you hope is installed.

Every agent pod runs the ctxmesh launcher as PID&nbsp;1. It scans input and output against the
referenced `GuardrailPolicy` — deterministic PII detectors, pattern denylists, an optional LLM
judge — and brokers every tool call, pausing the run when the `ApprovalPolicy` says a human signs
off first.

The contract is fail-closed. A dangling policy reference doesn't degrade to "unguarded" — it holds
the agent at `Ready=False`. There is no code path where an agent serves without the governance it
names.

<p class="feature-links">[Guardrails →](/guides/guardrails/) · [Approvals →](/guides/approvals/)</p>

</div>

```yaml
apiVersion: agents.ctxmesh.ai/v1beta1
kind: GuardrailPolicy
metadata:
  name: default-guardrails
spec:
  failMode: closed
  piiDetectors:
    builtIns: true
  patternDenylist:
    - name: prompt-injection
      pattern: "(?i)ignore (all|previous) instructions"
      action: block
      appliesTo: input
  userRateLimit:
    requestsPerMinute: 30
    spendUSD: "5.00"
```

<div class="feature-copy">

<p class="eyebrow">Quality &amp; rollout</p>

### No release ships on vibes.

Reference an `EvalSuite` and every candidate revision is scored against your dataset before it
serves — below threshold, the rollout is blocked and the old revision keeps serving. Pass, and a
canary takes a traffic split while online scores accumulate on both arms.

From there it's policy, not pager duty: auto-progress walks the canary up a percent ladder on
healthy verdicts; auto-rollback returns to the last healthy version the moment a regression is
detected.

<p class="feature-links">[Evals &amp; the deploy gate →](/guides/evals-and-the-deploy-gate/) · [Canary &amp; rollout →](/guides/canary-and-rollout/)</p>

</div>

```yaml
apiVersion: agents.ctxmesh.ai/v1beta1
kind: EvalSuite
metadata:
  name: support-quality
spec:
  dataset:
    ref: support-golden-set
  scorers:
    - name: correctness
      type: llm-judge
      weight: 3
    - name: format-check
      type: code
      weight: 1
  threshold: "0.85"
```

<section class="band feature-row">
<div class="feature-copy">

<p class="eyebrow">Observability</p>

### Every step, tool call, and token — without instrumenting your code.

A run is not a log line. ctxmesh records the causal tree — step → tool → model — with latency,
token counts, and cost on every node, plus human and judge feedback correlated back to the trace
that earned it.

You don't wire any of it. Framework spans come from base-image auto-instrumentation; the launcher
traces everything that crosses its endpoints. The same online scores that feed your dashboards gate
the next release.

## More than one agent. All still governed.

<div class="bento not-content">
  <article class="bento-card wide">
    <h3>Multi-agent, still governed</h3>
    <p><code>AgentTeam</code> gives a supervisor a roster and a spawn budget; <code>Workflow</code> declares graphs with typed error routing. Delegation inherits governance — a sub-agent can't do what its team may not.</p>
  </article>
  <article class="bento-card">
    <h3>Knowledge built in</h3>
    <p>A <code>KnowledgeBase</code> is upload → chunk → embed → index, granted by reference. RAG as a resource, not a pipeline you babysit.</p>
  </article>
  <article class="bento-card">
    <h3>Tenancy platform teams recognize</h3>
    <p><code>Tenant</code> groups namespaces with quotas and budgets. The console acts with <em>your</em> RBAC — caller-scoped, never a god service account.</p>
  </article>
  <article class="bento-card">
    <h3>Scale to zero, wake on demand</h3>
    <p>Serving on Knative, eventing on KEDA, batch as Jobs — the execution model is one field, and rollout adapts to each.</p>
  </article>
