<section class="band">

<p class="eyebrow">§ Why · the operational gap</p>

## Getting an agent to work is a weekend. Getting it to production is the job.

Which model, at what cost ceiling. What it may say and do. Who signs off before it
touches a payment API. How a new prompt is proven before it serves real traffic. What
exactly happened at 2&nbsp;a.m. when a run went sideways. Today every team answers these
with bespoke glue. ctxmesh makes each answer a resource — versioned, reviewed,
reconciled, and fail-closed when something's missing.

<dl class="spec-table not-content">
  <div><dt>Which model — fallback, budget?</dt><dd><code>ModelRoute</code></dd></div>
  <div><dt>What may it say? What must it never leak?</dt><dd><code>GuardrailPolicy</code></dd></div>
  <div><dt>Who approves the dangerous tool call?</dt><dd><code>ApprovalPolicy</code></dd></div>
  <div><dt>Is the new version actually better?</dt><dd><code>EvalSuite</code></dd></div>
  <div><dt>How does it reach 100% of traffic?</dt><dd><code>spec.rollout</code> <span class="muted">canary + auto-rollback</span></dd></div>
  <div><dt>What happened, step by step — and the cost?</dt><dd>the trace <span class="muted">no instrumentation</span></dd></div>
</dl>

<p class="eyebrow">§ Governance</p>

### Fail-closed, enforced in the pod — not middleware you hope is installed.

Every agent pod runs the ctxmesh launcher as PID&nbsp;1. It scans input and output
against the referenced `GuardrailPolicy` — deterministic PII detectors, pattern
denylists, an optional LLM judge — and brokers every tool call, pausing the run when
the `ApprovalPolicy` says a human signs off first.

A dangling policy reference doesn't degrade to "unguarded." It holds the agent at
<span class="hold-text">`Ready=False`</span>. There is no code path where an agent
serves without the governance it names.

<p class="feature-links">[Guardrails →](/guides/guardrails/) · [Approvals →](/guides/approvals/)</p>

</div>

```yaml
apiVersion: agents.ctxmesh.ai/v1beta1
kind: GuardrailPolicy
metadata:
  name: default-guardrails
spec:
  failMode: closed
  piiDetectors:
    builtIns: true
  patternDenylist:
    - name: prompt-injection
      pattern: "(?i)ignore (all|previous) instructions"
      action: block
      appliesTo: input
  userRateLimit:
    requestsPerMinute: 30
    spendUSD: "5.00"
```

<section class="band">

<p class="eyebrow">§ Quality &amp; rollout</p>

## No release ships on vibes.

Reference an `EvalSuite` and every candidate is scored against your dataset before it
serves. From there it's policy, not pager duty — the rollout walks a real sequence:

<ol class="ladder not-content">
  <li><span class="step">01</span><div><h4>Score</h4><p>The candidate revision runs your dataset. Below <code>threshold</code>, promotion is blocked and the old revision keeps serving.</p></div></li>
  <li><span class="step">02</span><div><h4>Canary</h4><p>A passing revision takes a traffic split while online scores accumulate on both arms.</p></div></li>
  <li><span class="step">03</span><div><h4>Auto-progress</h4><p>Healthy verdicts walk the canary up a percent ladder; a regression triggers auto-rollback to the last healthy version.</p></div></li>
  <li><span class="step">04</span><div><h4>Promoted</h4><p>The revision reaches 100%. The gate records the score that earned it.</p></div></li>
</ol>

<p class="feature-links">[Evals &amp; the deploy gate →](/guides/evals-and-the-deploy-gate/) · [Canary &amp; rollout →](/guides/canary-and-rollout/)</p>

</section>

<div class="feature-copy">

<p class="eyebrow">§ Observability</p>

### Every step, tool call, and token — without instrumenting your code.

A run is not a log line. ctxmesh records the causal tree — step → tool → model — with
latency, token counts, and cost on every node, plus human and judge feedback correlated
back to the trace that earned it.

You don't wire any of it. Framework spans come from base-image auto-instrumentation; the
launcher traces everything that crosses its endpoints. The same online scores that feed
your dashboards gate the next release.

<p class="feature-links">[Observability &amp; tracing →](/guides/observability-and-tracing/)</p>

</div>

<section class="band">

<p class="eyebrow">§ Scale &amp; teams</p>

## More than one agent. All still governed.

<div class="grid-cards not-content">
  <article><h3>Multi-agent, still governed</h3><p><code>AgentTeam</code> gives a supervisor a roster and a spawn budget; <code>Workflow</code> declares graphs with typed error routing. Delegation inherits governance — a sub-agent can't do what its team may not.</p></article>
  <article><h3>Knowledge as a resource</h3><p>A <code>KnowledgeBase</code> is upload → chunk → embed → index, granted by reference. RAG you declare, not a pipeline you babysit.</p></article>
  <article><h3>Tenancy platform teams know</h3><p><code>Tenant</code> groups namespaces with quotas and budgets. The console acts with <em>your</em> RBAC — caller-scoped, never a god service account.</p></article>
  <article><h3>Scale to zero, wake on demand</h3><p>Serving on Knative, eventing on KEDA, batch as Jobs — the execution model is one field, and rollout adapts to each.</p></article>
</div>
